# Arquitectura y decisiones de sesión

React AccessPage → API de identidad del mismo origen → SDK oficial Auth0 en Express → Universal Login. El callback vuelve a la pantalla de acceso independiente; nunca a `/app`. Las identidades usan los contratos de7A.1. La proyección autenticada lleva assurance=auth0-bff y applicationSubject=null: una sesión verificada no inventa un UUID de aplicación ni constituye autorización financiera. La frontera existente realFinancialAccess sigue denegando finanzas reales.

## BFF sin sesiones volátiles de servidor

Se elige el SDK oficial Express frente a introducir credenciales/refresh tokens en React. Utiliza sesiones **stateless en cookies cifradas/autenticadas por el SDK**, no un Map ni express-session MemoryStore. El propietario debe generar y conservar una clave aleatoria independiente por aplicación/entorno. Una nueva instancia del servidor con la misma clave puede leer la sesión; rotarla puede cerrar sesiones. No se genera una clave distinta en cada arranque ni se almacena en Git.

Cookie HttpOnly, SameSite=Lax, path=/ y host-only; Secure en HTTPS. HTTP sólo se permite para loopback de desarrollo, sin presentar esa configuración como producción. No se confía automáticamente en headers de proxy: un futuro proxy/TLS requiere configuración de confianza aprobada. No se incorporan contraseñas, tokens o secretos a localStorage/sessionStorage, IndexedDB, SQLCipher o bundles. El ID token queda dentro de la cookie cifrada del SDK; access/refresh tokens de la respuesta se descartan (campos vacíos exigidos por el tipo Session del SDK). No se pide offline_access ni audiencia de una API financiera.

Flujo Code, response_mode=query, PKCE S256, state y nonce gestionados por el SDK; issuer, audiencia del ID token y firma se verifican oficialmente. La API vuelve a comprobar issuer/audience del claim de la cookie para evitar confusiones de configuración. No se implementa criptografía propia. Los destinos son constantes de servidor con APP_BASE_PATH; no se aceptan returnTo, redirect_uri, issuer o connection arbitrarios del cliente.

Inicio, logout y reauth son POST con Origin exacto y content type permitido, comprobados antes del parser y del SDK; las cookies SameSite son una capa adicional. El callback GET usa la transacción de un uso del SDK, no esta regla Origin de POST. No hay CORS nuevo. Las respuestas llevan no-store y no-referrer; los errores del proveedor no se serializan ni registran. DEBUG configurado bloquea la activación de este módulo para no exponer datos del SDK por logs detallados. No ejecutar proxies que registren queries/códigos del callback.

## Caducidad, renovación y revocación

Sesión no rolling, máximo15min desde el callback y nunca más allá del exp del ID token. Se preservan sid y sessionExpiresAt del SDK. Si Auth0 aporta session_expiry, la proyección se limita también a ese techo con el margen conservador30s del SDK3.4; filtrar tokens no puede eliminar esa protección. Consultar la sesión no renueva su plazo. React revisa al cargar, recuperar foco/páginas y vencer el plazo; descarta respuestas tardías mediante AbortController y generación. La renovación es una autorización nueva **explícita**, con prompt=login y max_age=0. No se implementan refresh tokens ni renovaciones silenciosas. No se promete ausencia de paso de credenciales del proveedor social: deben probarse sus garantías reales con tenant.

Reauth liga el desafío de estado del SDK al subject actual, exige auth_time reciente y rechaza un subject distinto. Cambiar deliberadamente de método puede dar otra identidad, no vincularla; la interfaz lo explica y permite salir/reiniciar. El mismo correo no se usa para buscar, provisionar ni unir cuentas. El futuro UUID estable y bindings issuer/sub se resolverán en un registro confiable; mientras no exista, no se concede acceso financiero.

Logout elimina la cookie local y solicita logout de Auth0 mediante el SDK. Eso no prueba logout de Google/Apple ni revoca todos los tokens/copias de cookies. Las cookies stateless **no ofrecen revocación inmediata global**. Un grant rechazado o una reauth fallida elimina la sesión local; una revocación externa puede no observarse hasta reauth/caducidad. No se habilita backchannelLogout con un almacén volátil. Antes de beta se necesita diseñar/validar un registro persistente de revocaciones o una solución oficial equivalente, con costes/operación aprobados y pruebas reales. El límite temporal, bloqueo financiero y bloqueo de producción controlan esta limitación; no se presenta la sesión como autorización para operaciones sensibles reales.

La migración financiera/ownership/sincronización siguen en7B/7C. No hay rutas remotas financieras nuevas ni una segunda instancia de FinanceStore. El SDK sólo se ejecuta en rutas api/identity, manteniendo los endpoints existentes y su comportamiento.

La implementación instalada y su integridad están fijadas en package-lock.json.

Un callback espurio inválido no elimina por sí solo una sesión confirmada: los intentos legítimos de login/reauth ya retiran la sesión anterior en el POST protegido antes de redirigir. El SDK trata un callback sin transacción de una sesión ya autenticada como stale y redirige al origen sin procesar código/crear sesión; la prueba exige que la proyección completa no cambie. No se implementa un protocolo alternativo para ese caso. Se añadieron regresiones de cuerpo excesivo de otro origen y callback espurio, sin aceptar estados o identidades inválidas.
